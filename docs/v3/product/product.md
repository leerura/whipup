# V3 제품 범위와 결정

## 목표

사용자가 이해하기 쉬운 실제 보유 재료를 등록하고, 레시피가 포괄적으로 표현한 요구를 보유 재료와 합리적으로 연결한다. 사용자가 세부 종류를 잘못 선택하거나 같은 재료를 중복으로 등록한다고 느끼는 혼란을 줄인다.

## 확정된 결정

### 보유 재료는 사용자가 실제로 관리하는 단위로 등록한다

보유 재료 목록의 그룹 이름이 항상 등록 가능한 보유 항목인 것은 아니다. 각 그룹 아래에 실제로 보유할 수 있고 사용자가 알아볼 수 있는 선택 항목을 둔다. 그룹별 선택 항목은 재료 특성과 사용자의 관리 단위에 맞게 정한다.

예:

| 그룹 | 등록 가능한 보유 항목 예 | 그룹명 자체 선택 |
| --- | --- | --- |
| 간장 | 진간장, 국간장, 양조간장 | 불가 |
| 마늘 | 통마늘, 다진 마늘 | 불가 |
| 삼겹살 | 삼겹살, 대패삼겹살 | `삼겹살`은 일반적인 부위·보유 단위를 뜻하므로 가능 |

간장을 보유 재료 `간장` 하나로 통합하지 않는다. 종류가 구분되는 간장 제품은 사용자가 구체 종류로 등록한다. `형태 미지정`처럼 미확정 상태인 보유 항목을 별도로 추가하지 않는다.

`삼겹살` 예시는 그룹 제목과 같은 이름이라도 해당 명칭이 사용자에게 구체적인 실제 보유 단위를 뜻하면 선택 항목으로 둘 수 있음을 보여준다. 모든 그룹의 제목을 일괄적으로 선택 불가 처리하지 않는다.

현재 카탈로그 범위에서 포괄적인 `소고기` 및 `불고기용 소고기` 항목은 두지 않는다. 사용자가 실제로 관리하는 단위가 지나치게 넓고 모호하기 때문이다. `우삼겹`, `차돌박이`처럼 별도로 알아볼 수 있는 부위 항목은 이 결정만으로 제거 대상이 되지 않는다. 추출 결과에 포괄적인 소고기 항목이 필요해 보여도 에이전트가 카탈로그에 자동 재추가하지 않고 사용자 결정 대상으로 남긴다.

자취 요리 맥락에서 레시피 원문이 종류를 특정하지 않고 `참치`라고 하면 기본적으로 일반 `참치캔`을 뜻하는 것으로 보유 항목에 연결한다. `고추참치`는 별도로 등록할 수 있는 보유 항목이지만, 같은 참치 그룹이라는 이유만으로 일반 참치 요구를 자동 충족하지 않는다. 해당 레시피의 문맥이 고추참치 사용을 뒷받침할 때만 그 레시피의 충족 항목으로 연결한다.

`김`과 `김가루`는 하나의 `김` 그룹에서 각각 선택·등록한다. 두 항목은 사용자가 실제로 구분해 보유할 수 있으므로 selectable item으로 유지한다. 보유한 `김`은 부숴서 `김가루`로 준비할 수 있으므로, `김 → 김가루` 전역 준비 관계를 둔다.

위 재료명은 서로 다른 판단 결과를 설명하기 위한 사례일 뿐, 등록 가능한 재료의 전체 목록이나 다른 재료에 대한 분류 선례가 아니다. 새 재료를 판단할 때는 다음 기준을 각각 살핀다.

1. 사용자가 그 이름으로 실제 보유한 재료를 자연스럽게 알아볼 수 있는가?
2. 해당 종류를 구분하는 것이 보유 등록이나 레시피 충족 판정에 의미가 있는가?
3. 그룹 이름 자체가 포괄 분류명인지, 아니면 `삼겹살`처럼 구체적인 보유 단위도 자연스럽게 가리키는가?

예시 중 하나와 비슷해 보인다는 이유만으로 같은 선택 구조를 적용하지 않는다. 기준만으로 판단하기 어려운 재료는 임의로 일반화하지 않고 열린 결정으로 남긴다.

### 레시피 요구와 보유 재료는 별도로 표현한다

레시피의 `간장` 요구는 보유 재료 항목 `간장`을 뜻하지 않는다. 레시피 요구는 원문이 표현한 수준으로 남기고, 해당 레시피에서 그 요구를 충족할 수 있는 구체 보유 항목을 레시피별로 연결한다.

예를 들어 소스에서 `간장`이라고만 했다면 원문 요구 표현을 보존한다. 그 요구에 `진간장`, `양조간장` 중 어떤 보유 항목을 연결할지는 그 레시피의 전체 맥락을 보고 판단한다. 같은 판단을 전역 재료 규칙으로 만들지 않는다.

한 레시피 요구에 충족 가능한 구체 보유 항목이 여럿이면 여러 항목을 허용한다. 예: 특정 레시피의 `파` 요구가 대파와 쪽파 모두로 충족 가능하다고 판단되면 둘 다 해당 요구에 연결할 수 있다.

사용자도 같은 그룹 아래의 구체 보유 항목을 여러 개 동시에 등록할 수 있다. 예: 진간장과 국간장, 통마늘과 다진 마늘을 함께 보유할 수 있다. 그룹명 자체를 보유 항목으로 중복 등록한다는 뜻은 아니다.

### 요구 충족은 레시피 맥락에 따라 판단한다

판단은 재료 이름이나 영상에서 실제 사용된 재료 하나만으로 고정하지 않는다. 레시피의 전체 표현과 조리 맥락을 고려한다.

- 영상에 쪽파가 나온 사실만으로 대파는 쓸 수 없다고 단정하지 않는다.
- 영상에서 종류가 특정되지 않은 간장을 사용했다고 해서 임의로 진간장만 허용하거나, 모든 간장 종류가 항상 가능하다고 일반화하지 않는다.
- 맥락을 보아도 충족 항목을 합리적으로 결정하기 어려우면 검토 대상으로 표시한다.

검토가 해결되지 않은 필수 요구가 있는 Recipe는 `DRAFT`로 유지하고 추천에서 제외한다.

### 전역 재료 관계는 명확한 손질·준비 관계로 한정한다

전역으로 재사용할 관계는 보유 재료를 손질하거나 준비해 다른 형태로 만드는 관계에 한정한다. 예: 통마늘을 다져 다진 마늘로 준비한다.

`진간장 → 간장 요구`, `대파 → 파 요구`처럼 레시피 요구 충족 여부를 나타내는 관계는 전역 규칙으로 두지 않고 각 레시피의 요구에 기록한다.

### 새 보유 재료 항목은 검증 후 AI가 카탈로그에 추가할 수 있다

현재 V3 Ingredient catalog에 없는 selectable owned item이나 새 Ingredient group이 필요하면 사용자가 요청한 Codex 에이전트가 Gemini의 영상 추출 결과를 바탕으로 추가할 수 있다. Gemini 추출은 재료와 조리 정보의 원본 사실로 신뢰하며, 에이전트가 통상적으로 영상을 다시 대조하지 않는다. 새 항목은 재료 표시명, 사용자 보유 단위, 그룹 분류 기준에 따라 판단하고 deterministic validation을 통과해야 한다. 예시를 표면적으로 복사하지 않고 해당 재료 자체를 기준으로 판단한다.

새 selectable item/group이 추가된 레시피도 필수 요구 mapping이 완결되고 deterministic validation을 통과하면 `PUBLISHED`할 수 있다. 필수 mapping이나 catalog 분류를 합리적으로 확정할 수 없으면 추측해 추가·게시하지 않고 `DRAFT`로 남긴다. Gemini 추출 결과에 불확실성 또는 정보 부족이 명시된 경우에도 없는 내용을 만들어내지 않고 미해결 이유를 기록한다.

### 기존 요구 기능과 새 요구 연결을 구분한다

V2의 Recipe-declared Substitute와 Recipe-context Allowed Variant는 각각 기존 의미를 유지하며, V3의 레시피별 보유 항목 충족 판단과 혼합하지 않는다. 대체재가 이미 지원된다는 사실을 새 문제로 취급하지 않는다.

## V2에서 달라지는 핵심

- V2는 사용자 보유 단위와 Recipe Ingredient를 같은 Ingredient / Variant 체계로 연결하고, 간장은 하나의 `간장` Variant로 통합했다.
- V3는 간장처럼 사용자가 구분해 보유하는 종류를 별도 보유 항목으로 제공한다.
- 포괄적인 Recipe Requirement와 구체 보유 항목 사이의 충족 판정은 전역 Alias/Variant 규칙으로 고정하지 않고 레시피별로 기록한다.
- V3 데이터 전환 시 V2 운영 데이터는 초기화할 예정이므로 V1/V2 사용자 데이터 migration은 범위에 포함하지 않는다.

## 열린 결정

현재 남은 제품 결정은 없다. 운영상 추출 및 매핑 절차는 [레시피 데이터 파이프라인 명세](../development/recipe-pipeline.md)를 따른다.
