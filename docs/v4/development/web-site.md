# 웹 사이트 (검색·AI 유입)

Whippy 앱으로 사람을 데려오는 **읽기 전용 정적 웹 사이트**다. 앱을 대신하지 않는다. 재료 등록, 로그인, 개인화 추천은 웹에 두지 않는다.

## 목적과 원칙

1. **검색(사람)과 AI(LLM) 검색에 레시피 페이지가 걸린다.** 이 사이트의 유일한 목적이다.
2. 사람은 요리 이름이나 `레시피`로 검색하고, AI는 길고 자연스러운 질문을 하며 본문을 읽는다. 그래서 페이지 이름보다 **본문에 재료·순서·출처가 구조적으로 적혀 있는 것**을 우선한다.
3. 마케팅용 랜딩 페이지는 두지 않는다. 홈은 레시피 목록이다.
4. 서버와 DB를 쓰지 않는다. 빌드할 때 `data/`의 JSON을 읽어 정적 HTML을 만든다. 공개(`PUBLISHED`) 레시피만 올린다.

## 페이지

| 주소 | 내용 |
| --- | --- |
| `/` | 홈 = 레시피 목록(12개씩 페이지 이동), 검색창, "Whippy란?" 블록 |
| `/page/{n}/` | 목록 2페이지 이후 |
| `/recipes/{이름}-{영상ID}/` | 레시피 상세. 영상 임베드, 재료, 만드는 순서, 출처, 끝에 앱 안내 |
| `/about/` | 앱 소개: 한눈에 보기 표, 사용법, 이런 때 써요, 자주 묻는 질문, 문의 |
| `/sitemap.xml`, `/robots.txt`, `/llms.txt` | 검색·AI 크롤러용 |

- 앱 소개 페이지에는 **바뀌는 숫자(레시피·재료 개수)를 넣지 않는다.** 데이터가 바뀌어도 소개가 틀어지지 않게 하려는 것이다. 개수는 데이터에서 계산되는 목록 페이지에만 보인다.
- 재료별 페이지(`계란으로 만드는 요리` 등)와 같은 이름의 레시피를 묶는 "요리 모음" 페이지는 **만들지 않는다.** 사이트를 열고 4~6주 뒤 Search Console과 네이버 서치어드바이저의 실제 검색어를 보고 필요하면 그때 정한다.
- 같은 이름의 레시피는 제목 끝에 채널명을 붙여 구분한다(`김치볶음밥 - 살림팝`). 화면에 보이는 레시피 이름은 그대로다.

## 레시피 상세 내용

- 영상: YouTube 공식 임베드(`youtube.com/embed/{id}`)만 쓴다. 영상과 오디오를 내려받거나 저장하지 않는다. 채널명과 원본 영상 링크를 화면에 크게 표시한다.
- 재료·순서는 dataset의 값을 그대로 쓴다(`displayName`, 양, 단위, `steps`). 웹에서 새로 만들어 채우지 않는다.
- 한 문장 요약은 데이터에서 만든다: `{레시피 이름}: 재료 {n}개, {m}단계 레시피. 주요 재료는 {a}, {b}, {c}. 영상 출처: {채널명}.` 주요 재료는 필수 재료 순서대로 3개를 고르되 물·소금·간장 같은 기본 양념은 뒤로 미룬다. 없는 정보는 넣지 않는다.
- 재료의 양·단위가 데이터에 없으면 영상에서 읽은 원문 표현(`rawText`)을 보여 주고, 이름과 같으면 비워 둔다.
- 앱 설치 안내는 순서 아래에 둔다. 영상·재료 옆에 두지 않는다. 설치 버튼 옆에는 `iPhone용 무료 앱 · 회원가입 필요 없음`을 적는다.
- 푸터에 출처 안내와 **삭제 요청 연락처**를 둔다. 삭제 요청이 오면 해당 레시피를 비공개로 돌려 사이트를 다시 빌드한다.

## 검색 엔진·AI 노출

- 페이지마다 고유한 `<title>`과 `description`, 정규(canonical) 주소, 링크 미리보기(Open Graph)를 둔다.
- 구조화 데이터(JSON-LD): 레시피 상세에 `Recipe`(재료, 단계, 영상, 제작자=채널), 앱 소개에 `FAQPage`와 `MobileApplication`.
- AI가 인용하기 좋은 문장 규칙(GEO 연구의 방향): 구체적인 수치(레시피 개수, 재료 개수, 단계 수)와 출처를 본문 문장에 넣는다. 키워드를 반복해서 늘어놓지 않는다.
- "Whippy란?" 블록과 앱 소개의 정의 문장은 같은 표현을 쓴다: "냉장고에 있는 재료로 지금 만들 수 있는 요리를 추천해 주는 자취생용 iPhone 앱". 앱스토어 설명과 커뮤니티 글에서도 같은 표현을 쓴다.
- `llms.txt`는 만들되 효과를 기대하지 않는다(연구에서 인용 영향이 확인되지 않았다).
- 효과 측정: 한 달에 한 번 정한 질문 20개 정도를 여러 AI에 물어 Whippy가 나오는지 기록한다.

## 검색

- 정적 사이트이므로 빌드할 때 레시피 이름·채널·재료를 담은 작은 색인(`/search-index.json`)을 만든다. 브라우저에서 입력과 동시에 걸러 보여 준다. 서버 호출은 없다.

## 개발과 배포

- 위치: 저장소의 `web/`. Astro(정적 출력)를 쓴다. 로컬 실행은 `cd web && npm install && npm run dev`(주소 `http://127.0.0.1:4321`).
- 데이터: `../data/recipes/*.json`과 `../data/ingredients.json`을 빌드 때 읽는다. 사이트에서 데이터를 복사해 두지 않는다.
- 사이트 주소: `PUBLIC_SITE_URL` 환경 변수. 기본값은 로컬 주소이고, 배포 빌드에서는 `https://whippy.seokwonlee.xyz`를 준다.

### 호스팅: GitHub Pages

- 정적 사이트이고 서버·DB가 없다. 검색엔진 크롤러가 오는 사이트라 가동 시간이 중요하므로 앱 서버(Windows 노트북)와 분리해 GitHub Pages에 둔다. 저장소가 공개라서 무료이고 별도 계정이 필요 없다.
- 배포는 `.github/workflows/web.yml`이 한다. `main`에서 `web/`, `data/`, 이 워크플로가 바뀌면 `web/`을 빌드해 Pages에 올린다. 그래서 **레시피 데이터를 `main`에 반영하면 사이트도 자동으로 다시 배포**되고, 목록의 개수도 항상 최신이다. 수동 실행(`workflow_dispatch`)도 된다.
- Pages는 기본 브랜치(`main`)에서만 배포한다. 작업 브랜치의 변경은 `main`에 병합된 뒤 반영된다.
- 도메인: 가비아 DNS에 `whippy` CNAME → `leerura.github.io`. 저장소 Pages 설정의 커스텀 도메인에 `whippy.seokwonlee.xyz`를 넣고 "HTTPS 강제"를 켠다. 앱 서버 주소(`api.seokwonlee.xyz`)와는 별개의 레코드라 서로 영향이 없다.
- 삭제 요청이 오면 해당 레시피를 비공개(`DRAFT`)로 돌려 `main`에 반영한다. 반영하면 사이트에서도 내려간다.
