# 레시피 파이프라인 개편

이 문서는 V5에서 레시피 수집·반영 파이프라인을 고치는 목표와 원칙, 단계를 정한다. 추출 형식 변경은 V4에서 범위 밖이었고 V5에서 이 문서로 연다. 레시피 데이터 반영 판단 기준은 [레시피 데이터 반영 가이드](../../v4/development/recipe-data-guidelines.md)와 [수집 기준](../../v4/development/recipe-sourcing.md)을 따르고, 이 문서가 다르면 이 문서가 우선한다.

## 왜 하는가

추천 알림([알림](../product/notifications.md))이 사용자에게 "먹고 싶은 메뉴"를 제안하려면 사용자가 가진 재료로 만들 수 있는 **서로 다른 종류의 레시피가 충분히** 있어야 한다. 현재 파이프라인은 두 가지가 부족하다.

1. **수율**: 큐에 올린 영상 542개 중 28%는 쇼츠가 아니거나 정책상 제외되었고, 추출에 성공한 455개 중 공개된 것은 152개(약 33%)다. 최근 두 배치는 6%, 12%였다. Gemini 호출은 계정별 일일 한도가 있는 희소 자원이다.
2. **다양성**: 공개 레시피의 약 57%가 한 그릇 밥류(덮밥·볶음밥·비빔밥 등)이고 국·탕 3%, 카레 2%, 계란 요리 1%, 샌드위치·샐러드 0%다. 대표 재료로 만들 수 있는 요리가 거의 같은 종류로 몰린다.

## 목표

**다양성을 먼저, 수율은 그 안에서.** 수집 목표는 "공개 가능한 영상을 많이 얻는 것"이 아니라 "목표 분포를 채우는 레시피를 호출 한 번당 가장 효율적으로 얻는 것"이다.

## 원칙

- **원본 우선.** 영상 추출 원문(재료, 단계, 근거)은 재료 마스터에 매핑되지 않아도 버리지 않고 초안으로 보관한다. 필수 재료가 마스터에 없어서 공개하지 못하는 것은 실패가 아니라 대기 상태다.
- **재료 마스터는 일괄 검토한다.** 마스터 확장 기준은 지금 정하지 않는다. 파이프라인을 확장해 원본을 충분히 모은 뒤, 매핑되지 않은 재료 **전체**를 빈도, 해금되는 레시피 수, 자취생 기준으로 한 번에 검토해 정한다. 그 전에는 소규모 예외 승인 외에 마스터를 바꾸지 않는다.
- **판단은 기록하고 재사용한다.** 제외, 별칭, 이름, 분류 판단은 저장소의 데이터로 남긴다. 같은 판단을 대화나 일회용 스크립트에서 다시 하지 않는다.
- **편향을 점검한다.** 수율 같은 과거 성과만으로 수집을 조정하지 않는다(아래).

## 요리 종류 분류와 목표 비율 (초안, 검토 전)

| 종류 | 목표 비율 |
| --- | --- |
| 밥류(덮밥·볶음밥·비빔밥·주먹밥·김밥·죽) | 30% 이하 |
| 국·탕 | 10% |
| 찌개·전골 | 10% |
| 면·파스타 | 12% |
| 볶음·반찬 | 12% |
| 구이·조림·찜 | 8% |
| 계란 요리 | 5% |
| 전·부침·튀김 | 4% |
| 샌드위치·토스트·빵 | 4% |
| 카레·스튜 | 3% |
| 샐러드·무침 | 2% |

- 위 분류와 비율은 사용자가 검토해 확정하기 전의 초안이다. 확정되면 이 표를 고친다.
- 한 종류가 목표 비율을 넘으면 그 종류의 신규 수집을 멈춘다.
- 같은 레시피 이름은 신규 수집 기준으로 이름당 최대 2개까지 둔다(기존 데이터는 유지).
- 종류는 처음에는 이름 기준 규칙으로 분류하고, 추출 프롬프트 개선(3단계)에서 추출 결과로 받는다.

## 수집 예산 배분

- 호출 예산의 **70%는 활용**(기대 가치가 높은 채널·검색어), **30%는 탐험**(목표 비율에 비해 부족한 종류, 처음 가 보는 채널)에 쓴다.
- 채널·검색어별 수율은 **참고 신호**일 뿐 수집 목표가 아니다. 표본이 적은 채널(예: 10건 미만)은 평균 수율을 그대로 믿지 않고 불확실성을 반영해 탐험 쪽으로 보낸다.
- 수율은 채널별뿐 아니라 **요리 종류별**로도 본다. 국물 요리의 낮은 수율이 영상 탓인지 재료 마스터 탓인지 구분한다.
- 정기적으로 선택된 수집과 선택되지 않은 수집의 분포를 비교해 편향(인기 채널 쏠림, 특정 종류 쏠림)을 점검한다.

## 지표

- 종류별 레시피 비율과 목표 대비 차이
- 단계별 수율(큐 → 쇼츠·임베드 → 추출 → 반영 → 공개)과 채널별·종류별 수율
- **사용자 관점 다양성**: 대표 재료 조합 N개에서 바로 만들 수 있는 후보가 **몇 가지 종류**로 나뉘는가, 후보가 1개 이상 나오는 실제 사용자 비율. 알림 출시 조건([알림](../product/notifications.md#출시-조건))에 쓴다.

## 단계

1. **반영 도구와 제외 목록.** 일회용 스크립트로 하던 반영(재료 매핑, 이름, 단위 정리, 출처 보충, 상태 분류, 검증)을 저장소의 결정적인 도구로 옮긴다. 별칭 표와 제외 목록은 구조화된 데이터로 두고, 같은 입력이면 같은 결과가 나오게 한다. 반영 결과는 "공개 / 재료가 추가되면 공개 가능 / 영구 초안"으로 분류하고 이유를 보고서로 남긴다. 한 번 제외한 영상이 다시 반영되지 않게 한다. 재료별 해금 효과(어떤 재료가 몇 개 레시피를 푸는가)를 자동으로 만든다.
2. **분류 체계, 예산 배분, 대시보드.** 요리 종류 분류와 목표 비율을 코드에 반영하고, 수집 예산 배분과 위 지표 대시보드를 만든다.
3. **추출 프롬프트와 큐 정리.** 추출 결과에 **짧은 레시피 이름, 주재료, 요리 종류, 조리 여부**를 추가해 이름 줄이기를 없애고 품질 검사를 자동화한다. 영상 대기열을 주석이 섞인 텍스트 대신 구조화된 형식으로 바꾸고, 실시간으로 바뀌는 진행 상태 파일(`workers.json`, `runtime.json`)은 Git 추적에서 뺀다.

## 1단계 반영 도구 (`tools/data-pipeline/src/apply.py`)

- **두 단계로 나눈다.** `apply.py fetch`만 네트워크를 쓴다(쇼츠·임베드 확인, 채널 이름·사진). 확인된 사실은 체크포인트의 `applyChecks`, `sourceMetadata`에 저장하고, 쇼츠가 아니거나 임베드가 막힌 영상은 `rules/exclusions.json`에 기록한다. 확인하지 못한 값은 저장하지 않고 다음 실행에서 다시 묻는다. `apply.py plan`은 네트워크 없이 체크포인트, 데이터셋, 규칙 파일만 읽으므로 같은 입력이면 같은 결과가 나온다. `--write`를 붙일 때만 파일을 쓰고, 반영 결과는 Git diff로 사람이 확인한다.
- **판단 기록 파일**(`tools/data-pipeline/rules/`): `exclusions.json`(다시 반영하지 않을 영상과 이유), `aliases.json`(같은 재료의 다른 표기만, 대상은 카탈로그 이름), `names.json`(승인한 레시피 이름), `policy.json`(자취생 기준에서 뺀 재료 단어, 파생 재료, 영어 단위, 기준 숫자).
- **매핑은 검토된 데이터만 쓴다.** 카탈로그 이름, 카탈로그 별칭, `aliases.json`만 쓴다. 다른 레시피의 매핑을 끌어다 쓰지 않는다(V3 데이터 스키마: 레시피별 매핑은 각자 판단). `apply.py suggest-aliases`는 공개 레시피에서 별칭 후보를 뽑아 보여 주기만 하고, 사람이 승인해 `aliases.json`에 넣는다.
- **반영 결과 분류.** 위 단계 1의 세 분류를 다음 네 가지로 구체화한다. 원본은 어느 경우든 체크포인트에 남는다.
  - **공개**: 모든 필수 재료가 정확히 매핑되고 품질 검사를 통과. `PUBLISHED`로 쓴다.
  - **재료가 추가되면 공개 가능**: 카탈로그에 없는 필수 재료만 남음. `DRAFT`로 쓴다(원본 우선).
  - **사람 확인 필요**: "또는" 같은 대체 재료 표기(원문에만 있는 경우 포함), "간장"처럼 여러 종류를 묶은 이름, 카탈로그 이름과 비슷한 미매핑 재료(별칭인지 새 재료인지), Gemini가 남긴 불확실한 점(`unresolved`, 단 분량·단위만 빠졌다는 메모는 막지 않는다: 사용자 결정 2026-11-22), 영어 단위, 이름 미승인, 같은 이름 2개 초과, 필수 재료 3개 이하, 가열·조리 단계 없음, 출처 누락, 쇼츠·임베드 미확인. 데이터셋에 쓰지 않고 보고서에 이유를 남긴다.
  - **반영 안 함**: 제외 목록에 있거나, Git 기록상 사람이 지운 레시피이거나, 자취생 기준에서 뺀 재료가 필요하거나, 추출 결과 형식이 잘못됨.
- **기존 초안은 덮어쓰지 않는다.** 매핑이 비어 있는 재료만 채우고(표시 이름은 카탈로그 이름으로), 새 레시피와 같은 품질 검사를 통과한 것만 보고서에 "이제 공개 가능"으로 보여 준다. `plan --promote <영상 ID>`로 지정한 것만 쓰고(`--write`와 별개), 목록에 없는 ID를 주면 아무것도 쓰지 않고 멈춘다. 사람이 고친 매핑, 이름, 단계는 그대로 둔다.
- **막고 있는 재료 표**는 종류(묶음 이름, 제외 단어, 대체 재료 표기, 카탈로그와 비슷함)를 함께 보여 준다. 종류가 비어 있는 것만 새 재료 후보로 본다.
- **기존 공개 레시피는 지우지 않는다.** 현재 규칙과 맞지 않는 공개 레시피는 보고서에 목록으로만 보여 준다.
- 레시피 파일은 Python 검증기(`recipe_rules.validate_recipe`, 백엔드 `DatasetLoader` 규칙과 같음)를 통과해야 쓴다. 레시피와 영상은 키가 아니라 `shortsReference`의 영상 ID로 맞춘다.

## 2단계 분류, 예산, 지표 (`tools/data-pipeline/src/collection.py`)

- **분류와 목표 비율**은 `rules/dish-types.json`에 둔다(위 표와 같은 값, 종류 코드는 3단계 `dishType`과 같다). 종류는 수동 지정(`overrides`) → Gemini `dishType`(추출 버전 2) → 이름 규칙 순으로 정한다. 이름 규칙은 위에서부터 처음 맞는 종류를 쓰며, 밥으로 먹는 요리는 밥류가 먼저다.
- **목표 초과 종류는 신규 수집을 멈춘다.** 공개 레시피 중 비율이 목표를 넘은 종류는 `discover.py`가 후보 제목을 분류해 거른다(`--allow-over-target`으로만 끈다). 제목은 해시태그·대괄호·이모지를 지운 뒤 분류하고, 걸러낸 제목은 사람이 볼 수 있게 출력한다. 제목 분류는 근사치라서 걸러지지 않은 후보도 반영 단계에서 다시 종류를 본다.
- **예산 배분** `collection.py plan --budget N`: Gemini 호출 N회 중 70%는 추출 10건 이상인 채널에 기대 수율 비례로(한 채널은 활용 몫의 35%까지), 30%는 목표 대비 부족한 종류의 검색어(`exploreQueries`)와 표본이 적거나 처음 가 보는 채널에 배분한다. 기대 수율은 전체 수율 쪽으로 표본 10건만큼 끌어당긴 값이라 2건 중 2건 같은 작은 표본이 앞서지 않는다. 채널 수율은 지금 수집하는 종류(목표 초과 종류를 뺀 것)의 영상만으로 계산해, 밥류에 강한 채널이 계속 예산을 가져가는 되먹임을 막는다. 표본이 적은 채널은 수율이 아니라 표본이 적은 순서로 보여 주고, 탐험 검색어는 덜 쓴 것부터 고른다. 계획은 실행할 `discover.py` 명령을 보여 줄 뿐 자동으로 돌리지 않는다.
- **지표** `collection.py metrics [--write]`(V3 추출 전에 사람이 검토한 옛 영상은 단계 수율에서 뺀다)(파이프라인 대시보드 `/metrics`에도 같은 내용): 단계별 수율, 종류별 비율과 목표 차이, 종류별·채널별·검색어별 수율(90% 범위 포함), 종류별로 공개되지 못한 이유(재료 미매핑 / 정책·제외), 편향 점검(추출과 공개의 종류 분포 비교, 상위 채널 비중), 사용자 관점 다양성.
- **사용자 관점 다양성**은 `rules/sample-inventories.json`의 대표 재료 조합(초안)으로 바로 만들 수 있는 공개 레시피 수와 종류 수를 센다. 재료 관계는 넣지 않은 보수적인 근사치다. 알림 출시 조건의 "후보가 1개 이상인 실제 사용자 비율"은 운영 데이터가 필요해 여기서 다루지 않는다.

## 3단계 추출 프롬프트와 큐 정리

- **추출 결과 분류 필드(추출 버전 2).** Gemini가 레시피 원문과 함께 다음을 돌려준다. 버전 1 체크포인트에는 없으며, 다시 추출하지 않는다.
  - `recipeName`: 메뉴에 보일 짧은 요리 이름(약 9자, 꾸밈말·해시태그 없음). 반영 도구는 승인한 이름(`names.json`)이 없으면 이 이름을, 그것도 규칙에 안 맞으면 영상 제목을 쓰고, 둘 다 안 되면 이름 승인을 요청한다.
  - `dishType`: 요리 종류 하나. 위 목표 비율 표와 같은 분류다: `RICE` 밥류, `SOUP` 국·탕, `STEW` 찌개·전골, `NOODLE` 면·파스타, `STIR_FRY_SIDE` 볶음·반찬, `GRILL_BRAISE_STEAM` 구이·조림·찜, `EGG` 계란 요리, `PANCAKE_FRIED` 전·부침·튀김, `BREAD` 샌드위치·토스트·빵, `CURRY` 카레·스튜, `SALAD` 샐러드·무침, `OTHER` 그 밖(디저트·음료 등). 2단계 분류와 수집 예산에 쓴다.
  - `mainIngredients`: 요리를 정하는 재료 1~3개(재료 목록의 `displayName`을 그대로). 양념·기름·물은 넣지 않는다. 알림의 핵심 재료 판단에 쓸 수 있다.
  - `requiresCooking`: 불이나 기기(가스레인지, 전자레인지, 오븐, 에어프라이어, 밥솥, 끓는 물)를 쓰면 `true`. `false`면 사람 확인으로 보낸다. 값이 없는 버전 1 결과에는 기존 단어 기준 검사를 쓴다.
  - 분류 필드 형식이 틀리면 레시피를 버리지 않고 사람 확인으로 보낸다. 분류 필드는 체크포인트에만 있고 레시피 파일(`data/recipes`)에는 넣지 않는다(백엔드가 모르는 필드를 거부한다).
- **영상 대기열** `tools/data-pipeline/input/queue.jsonl`: 한 줄에 영상 하나인 JSON(`videoId`, `url`, `source`: `manual`·`discover-channel`·`discover-search`, 있으면 `addedAt`, `batch`, `channel`, `title`, `views`, `subscribers`, `query`). 항목은 지우지 않아서 제출한 모든 영상의 기록이 된다. 추출하지 않을 영상은 주석으로 막지 않고 `rules/exclusions.json`에 이유와 함께 넣으며, 파이프라인은 제외 목록에 있는 영상을 건너뛴다. 채널·검색어 정보는 2단계 수율 분석에 쓴다. 예전 `shorts-urls.txt`는 이 형식으로 옮겼고 주석으로 막혀 있던 판단은 모두 제외 목록으로 옮겼다.
- 영상을 손으로 넣을 때는 `python3 src/video_queue.py add <URL> [--note 메모]`를 쓴다(영상 ID, 출처, 날짜를 채운다). 제외 목록을 읽을 수 없으면 파이프라인은 "제외 없음"으로 보지 않고 마지막으로 읽은 목록을 쓰며, 처음부터 읽을 수 없으면 추출을 멈추고 대시보드에 알린다.
- Gemini `recipeName`은 9자 이하 한글 이름이고 꾸밈말(초간단, 레시피, "3분" 등)이 붙어 있지 않을 때만 그대로 쓴다. 같은 이름 개수는 띄어쓰기를 무시하고 센다. 조리 여부는 Gemini가 `false`라고 하거나 조리 단계에 가열 단어가 없으면 사람 확인으로 보낸다.
- **실시간 상태 파일**(`state/workers.json`, `state/runtime.json`, `state/.*.lock`)은 Git에서 추적하지 않는다. 영상별 체크포인트(`state/<영상 ID>.json`)는 계속 추적한다.
- **이 변경을 파이프라인이 도는 컴퓨터에 처음 반영할 때**는 파이프라인을 멈춘 뒤 받는다. 실행 중에 받으면 잠금 파일이 지워져 같은 영상을 두 번 추출할 수 있다.
  1. `docker compose stop recipe-pipeline`
  2. `git checkout -- tools/data-pipeline/state/workers.json tools/data-pipeline/state/runtime.json`
  3. `git pull`
  4. `docker compose up -d --build recipe-pipeline` (이미지가 `src/`를 복사하므로 다시 빌드해야 새 대기열을 읽는다)

## 자동 품질 검사

공개 전에 자동으로 확인한다: 쇼츠 여부와 임베드 가능 여부, 출처(채널명·사진), 필수 재료 3개 이하, 조리 과정이 사실상 없음(섞기만 하는 수준), 영어 단위, 이름 길이 규칙, 단계가 문자열인지.

## 이번에 하지 않는 것

- 고기 재료 관리 방식 변경(레시피가 쌓인 뒤 다시 논의).
- 재료 마스터 확장 기준을 지금 확정하는 것(원본을 모은 뒤 일괄 검토).
