# 레시피 파이프라인 개편

이 문서는 V5에서 레시피 수집·반영 파이프라인을 고치는 목표와 원칙, 단계를 정한다. 추출 형식 변경은 V4에서 범위 밖이었고 V5에서 이 문서로 연다. 레시피 데이터 반영 판단 기준은 [레시피 데이터 반영 가이드](../../v4/development/recipe-data-guidelines.md)와 [수집 기준](../../v4/development/recipe-sourcing.md)을 따르고, 이 문서가 다르면 이 문서가 우선한다.

## 왜 하는가

추천 알림([알림](../product/notifications.md))이 사용자에게 "먹고 싶은 메뉴"를 제안하려면 사용자가 가진 재료로 만들 수 있는 **서로 다른 종류의 레시피가 충분히** 있어야 한다. 현재 파이프라인은 두 가지가 부족하다.

1. **수율**: 큐에 올린 영상 542개 중 28%는 쇼츠가 아니거나 정책상 제외되었고, 추출에 성공한 455개 중 공개된 것은 152개(약 33%)다. 최근 두 배치는 6%, 12%였다. Gemini 호출은 계정별 일일 한도가 있는 희소 자원이다.
2. **다양성**: 공개 레시피의 약 57%가 한 그릇 밥류(덮밥·볶음밥·비빔밥 등)이고 국·탕 3%, 카레 2%, 계란 요리 1%, 샌드위치·샐러드 0%다. 대표 재료로 만들 수 있는 요리가 거의 같은 종류로 몰린다.

## 목표

**다양성을 먼저, 수율은 그 안에서.** 수집 목표는 "공개 가능한 영상을 많이 얻는 것"이 아니라 "목표 분포를 채우는 레시피를 호출 한 번당 가장 효율적으로 얻는 것"이다.

## 원칙

- **원본 우선.** 영상 추출 원문(재료, 단계, 근거)은 재료 마스터에 매핑되지 않아도 버리지 않고 초안으로 보관한다. 필수 재료가 마스터에 없어서 공개하지 못하는 것은 실패가 아니라 대기 상태다.
- **재료 마스터는 일괄 검토한다.** 마스터 확장 기준은 지금 정하지 않는다. 파이프라인을 확장해 원본을 충분히 모은 뒤, 매핑되지 않은 재료 **전체**를 빈도, 해금되는 레시피 수, 자취생 기준으로 한 번에 검토해 정한다. 그 전에는 소규모 예외 승인 외에 마스터를 바꾸지 않는다.
- **판단은 기록하고 재사용한다.** 제외, 별칭, 이름, 분류 판단은 저장소의 데이터로 남긴다. 같은 판단을 대화나 일회용 스크립트에서 다시 하지 않는다.
- **편향을 점검한다.** 수율 같은 과거 성과만으로 수집을 조정하지 않는다(아래).

## 요리 종류 분류와 목표 비율 (초안, 검토 전)

| 종류 | 목표 비율 |
| --- | --- |
| 밥류(덮밥·볶음밥·비빔밥·주먹밥·김밥·죽) | 30% 이하 |
| 국·탕 | 10% |
| 찌개·전골 | 10% |
| 면·파스타 | 12% |
| 볶음·반찬 | 12% |
| 구이·조림·찜 | 8% |
| 계란 요리 | 5% |
| 전·부침·튀김 | 4% |
| 샌드위치·토스트·빵 | 4% |
| 카레·스튜 | 3% |
| 샐러드·무침 | 2% |

- 위 분류와 비율은 사용자가 검토해 확정하기 전의 초안이다. 확정되면 이 표를 고친다.
- 한 종류가 목표 비율을 넘으면 그 종류의 신규 수집을 멈춘다.
- 같은 레시피 이름은 신규 수집 기준으로 이름당 최대 2개까지 둔다(기존 데이터는 유지).
- 종류는 처음에는 이름 기준 규칙으로 분류하고, 추출 프롬프트 개선(3단계)에서 추출 결과로 받는다.

## 수집 예산 배분

- 호출 예산의 **70%는 활용**(기대 가치가 높은 채널·검색어), **30%는 탐험**(목표 비율에 비해 부족한 종류, 처음 가 보는 채널)에 쓴다.
- 채널·검색어별 수율은 **참고 신호**일 뿐 수집 목표가 아니다. 표본이 적은 채널(예: 10건 미만)은 평균 수율을 그대로 믿지 않고 불확실성을 반영해 탐험 쪽으로 보낸다.
- 수율은 채널별뿐 아니라 **요리 종류별**로도 본다. 국물 요리의 낮은 수율이 영상 탓인지 재료 마스터 탓인지 구분한다.
- 정기적으로 선택된 수집과 선택되지 않은 수집의 분포를 비교해 편향(인기 채널 쏠림, 특정 종류 쏠림)을 점검한다.

## 지표

- 종류별 레시피 비율과 목표 대비 차이
- 단계별 수율(큐 → 쇼츠·임베드 → 추출 → 반영 → 공개)과 채널별·종류별 수율
- **사용자 관점 다양성**: 대표 재료 조합 N개에서 바로 만들 수 있는 후보가 **몇 가지 종류**로 나뉘는가, 후보가 1개 이상 나오는 실제 사용자 비율. 알림 출시 조건([알림](../product/notifications.md#출시-조건))에 쓴다.

## 단계

1. **반영 도구와 제외 목록.** 일회용 스크립트로 하던 반영(재료 매핑, 이름, 단위 정리, 출처 보충, 상태 분류, 검증)을 저장소의 결정적인 도구로 옮긴다. 별칭 표와 제외 목록은 구조화된 데이터로 두고, 같은 입력이면 같은 결과가 나오게 한다. 반영 결과는 "공개 / 재료가 추가되면 공개 가능 / 영구 초안"으로 분류하고 이유를 보고서로 남긴다. 한 번 제외한 영상이 다시 반영되지 않게 한다. 재료별 해금 효과(어떤 재료가 몇 개 레시피를 푸는가)를 자동으로 만든다.
2. **분류 체계, 예산 배분, 대시보드.** 요리 종류 분류와 목표 비율을 코드에 반영하고, 수집 예산 배분과 위 지표 대시보드를 만든다.
3. **추출 프롬프트와 큐 정리.** 추출 결과에 **짧은 레시피 이름, 주재료, 요리 종류, 조리 여부**를 추가해 이름 줄이기를 없애고 품질 검사를 자동화한다. 영상 대기열을 주석이 섞인 텍스트 대신 구조화된 형식으로 바꾸고, 실시간으로 바뀌는 진행 상태 파일(`workers.json`, `runtime.json`)은 Git 추적에서 뺀다.

## 자동 품질 검사

공개 전에 자동으로 확인한다: 쇼츠 여부와 임베드 가능 여부, 출처(채널명·사진), 필수 재료 3개 이하, 조리 과정이 사실상 없음(섞기만 하는 수준), 영어 단위, 이름 길이 규칙, 단계가 문자열인지.

## 이번에 하지 않는 것

- 고기 재료 관리 방식 변경(레시피가 쌓인 뒤 다시 논의).
- 재료 마스터 확장 기준을 지금 확정하는 것(원본을 모은 뒤 일괄 검토).
